## 1. 项目定位

### 1.1 要解决的问题

腾讯桌面整理的格子确实好用，但它捆着魔镜壁纸、云盘、AI 问答、内嵌浏览器、更新与遥测一整
套模块：**3 个进程、180 MB 内存、700 MB 磁盘**。本项目只留下「格子 + 按规则自动归类 + 桌面
搜索」这三件每天真在用的事。

### 1.2 功能范围（5 个模块）

| 模块 | 内容 | 对应 DeskGo 组件 |
|---|---|---|
| **桌面整理** | 格子、按类型码自动归类、拖拽、折叠收展、变更监听、接管桌面图标 | `DesktopMgr64.exe` + `Features64.dll` |
| **桌面搜索** | 文件名子串 + 拼音首字母、全局热键唤起、右键菜单唤起 | `DesktopSearch64.exe` + `DiskSearchCore64.dll` |
| **设置** | 基础 / 桌面 / 右键集成 三页 | `DesktopSettings.exe` |
| **右键集成** | 桌面背景、文件/文件夹级联菜单；菜单风格切换（Win11 / 经典净化） | `DeskMgrShellExtx64.dll` + `Win11ContextMenu.exe` |
| **支撑层** | 数据持久化 + 日/周/月滚动备份、单实例、命令总线、冲突检测、图标缓存、崩溃自愈 | `QMIpc64.dll`、`QMLogEx64.dll` |

### 1.3 明确**砍掉**的部分

壁纸（魔镜壁纸 / 挂件 / 壁纸库）、云与 AI（一键上云 / AI 问答 / AI 便签 / IM）、
内容（内嵌 CEF 浏览器 / TBS / 下载中心），以及原版的更新、下载加速、自保护、遥测上报体系。

### 1.4 法律与合规边界（务必保持）

- 个人学习性质，用于研究 **Win32 桌面层接管、分层窗口渲染、图标提取**等技术。
- **不包含腾讯公司的任何代码、二进制文件、图标或美术资源**；仅参考公开可见的交互行为与界面观感。
- 与腾讯公司及其产品**无任何关联**，未获授权或认可。

## 3. 技术架构

### 3.1 技术选型与理由

| 选型 | 取值 | 理由 |
|---|---|---|
| 框架 | .NET 7 WinForms | 需要大量 Win32 P/Invoke；WinForms 提供托盘/消息循环/窗口宿主，且比 WPF 轻 |
| 发布 | 框架依赖（`SelfContained=false`） | 产物仅数百 KB，复用系统运行时 |
| 语言 | C# 11 / `Nullable enable` | 全项目可空引用类型保护 |
| 权限 | `asInvoker`（`app.manifest`） | 全程普通用户，不碰需要管理员的方案 |

### 3.2 分层结构

```
┌──────────────────────────────────────────────────────────────┐
│ 表现层 UI/                                                    │
│   MainContext  托盘主控制器·进程总枢纽·生命周期·资源自管        │
│   BoxForm      格子窗口壳：分层渲染·拖动·折叠·尺寸·右键菜单      │
│   BoxView      格子内容视图：完全自绘 · 命中测试 · 多选          │
│   RenameBox    就地改名小窗（独立顶层窗口，绕开分层窗口限制）      │
│   SearchForm / SettingsForm / SnapOverlay                     │
├──────────────────────────────────────────────────────────────┤
│ 领域层 Core/                                                  │
│   Model / Rules / DeskData / DataStore / Settings             │
│   DesktopScanner / VirtualItems / Pinyin                      │
│   CmdBus / ShellIntegration / Startup / Conflict / CrashGuard  │
├──────────────────────────────────────────────────────────────┤
│ 平台层 Win32/                                                 │
│   Native          全部 P/Invoke 声明集中于此                   │
│   DesktopHost     桌面窗口链定位·图标枚举·隐藏恢复·保活          │
│   ShellMenu       原生右键菜单宿主（IContextMenu 1/2/3）        │
│   MemInfo         内存/句柄/GDI 诊断快照                       │
├──────────────────────────────────────────────────────────────┤
│ 诊断层 Cli/Diagnostics   20+ 自检命令（不参与常驻运行）          │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向单向向下**：UI → Core → Win32。Core 层不引用 `UI/` 与 `Win32/`
（只通过 `Core/CmdBus`、`DesktopScanner` 等少数桥接点间接使用平台能力）。

### 3.3 运行时模型

#### 3.3.1 进程与线程

```
DeskLite.exe（唯一进程 · 单实例互斥体守护）
├── UI 线程（STA）
│     ├── Application.Run(MainContext)
│     ├── 所有窗口（格子 / 托盘 / 搜索 / 设置 / 改名小窗）
│     └── 所有 System.Windows.Forms.Timer 的 Tick 都在这里
├── FileSystemWatcher 回调线程（.NET 线程池）
│     └── 只做「投递到 UI 线程」，绝不在工作线程建 WinForms 定时器
├── GC 线程（并发 GC 已关闭，仅保留必要线程）
└── 合计 15 个线程左右（主要是运行时自身的）
```

> **没有自建后台线程**。所有业务逻辑都在 UI 线程执行，避免跨线程 UI 访问问题。
> 这是刻意的：本程序的耗时操作（扫描桌面、取图标）在 60 项规模下是**亚秒级**的，
> 引入线程池只会换来同步复杂度，换不到可感知的收益。

#### 3.3.2 常驻计时器（CPU 占用的全部来源）

| 计时器 | 间隔 | 职责 | 开销 |
|---|---|---|---|
| 保活巡检 `_keepAlive` | 800 ms → **3000 ms**（连续 20 次无事自动退避） | `EnsureLocated()` + `EnsureIconsHidden()` | 每次 2～3 个 API 调用，**零分配** |
| 空闲整理巡检 `_idleTimer` | **5000 ms**（刚活动过临时切 **2000 ms**，稳定后自动放稀） | 三道闸门判定后整理内存 | 大多数 tick 只读一个计数器 |
| 文件变更去抖 `_debounce` | 900 ms（事件触发后单次） | `RefreshAll(force: false)` | 指纹未变则直接返回 |
| 启动整理 `ScheduleStartupSettle` | 2000 ms（一次性） | 释放图标池 + 完整 GC + 交还工作集 | 只跑一次 |

**这就是「空闲 CPU 0.000%」的原因**：常态下每秒最多 0.33 次极轻量巡检，且全部在 UI 线程
按需触发，没有轮询式的重活。

> `_idleTimer` 的两档间隔是刻意的：一直用 2 秒会把常驻 CPU 从 0.00x% 抬到约 0.04%
> （唤醒频率 ×2.5），而长期空闲时根本没必要这么勤。所以只有「刚活动过」才加密，
> 一旦工作集落回水位线就自动放稀 —— 既保住了回落速度，又保住了空闲 CPU。

#### 3.3.3 启动时序

```
① CrashGuard.Init()                    全局异常处理器（必须最先）
② 单实例互斥体                          已在跑 → 弹提示退出
③ CrashGuard.RecoverIfNeeded()         上次崩溃则先还原桌面图标
④ MainContext 构造
   ├─ Pinyin.Init()                     GB2312 码表
   ├─ AppSettings.Load()                ConFile.dat
   ├─ IconCache 建立                    （此时还不取图标）
   ├─ DataStore.Load()                  格子模型 + schema 迁移
   ├─ EnsureSystemBox()                 补建系统格子（挑不相交落点）
   ├─ DesktopHost.Locate()              定位 Progman→DefView→SysListView32
   ├─ Conflict 检测                     DeskGo 进程 + 覆盖层
   ├─ 托盘 + 菜单 + 命令总线
   ├─ CreateBoxes()                     创建格子窗口
   ├─ RefreshAll()                      ★ 扫描 + 分组 + 首次取全部图标
   ├─ StartWatcher / StartKeepAlive / ApplyHotkey
   └─ ScheduleStartupSettle()           2 秒后做一次性内存整理
⑤ ToggleTakeover()                     隐藏原生图标，格子接管
⑥ ToggleEmbed()（可选）                 SetParent 到 Progman
⑦ Application.Run()                    消息循环
```

实测：④ 全流程约 **0.8 秒**（含取 58~60 个图标）。

### 3.4 六大关键机制

#### 3.4.1 桌面图标接管

```
隐藏侧：ShowWindow(SysListView32, SW_HIDE)  → 立刻写「桌面已隐藏」标记落盘
保活侧：每 0.8s / 3s 巡检 IsWindowVisible，被 explorer 恢复就再隐藏
自愈侧：崩溃/强杀后，下次启动 RecoverIfNeeded() 无条件还原
退出侧：托盘「退出并还原桌面」→ ShowWindow(SW_SHOW) + 清标记
```

三层防护缺一不可：explorer 会**异步**把 ListView 恢复成可见（所以需要保活）；进程可能
被强杀（所以需要落盘标记 + 启动自愈）；正常退出必须还原（所以退出路径单独走一遍）。

> ⚠️ **本轮实测发现**：进程被**强杀**（非 `--quit`）时，桌面图标会一直保持隐藏直到下次
> 启动 DeskLite 才会被还原。这期间用户看到的是「桌面空了」。属于已知风险，见 6.3。

#### 3.4.2 逐像素 alpha 分层渲染（毛玻璃）

这是本项目最核心的技术点：**只有底板透明，图标与文字保持满格清晰**。

| | 旧：`Form.Opacity` | 现：`UpdateLayeredWindow` |
|---|---|---|
| 机制 | `SetLayeredWindowAttributes(LWA_ALPHA)` | 32bpp ARGB 位图逐像素提交 |
| alpha 粒度 | 整窗**一个常数** | **每像素各自 alpha** |
| 调透明度的后果 | 底板 + 图标 + 文字一起变淡 | 只有底板变，图标文字不受影响 |

```
GDI+ 画到 32bpp ARGB 位图  →  LockBits 拷进 DIB section  →  UpdateLayeredWindow 提交
        （底板带 alpha）            （保留 alpha）            （ULW_ALPHA + AC_SRC_ALPHA）
```

**三个必须避开的坑**：

1. **不能用 `Bitmap.GetHbitmap()`** —— 它产出 `Format32bppRgb`，**alpha 会被丢掉**。
   必须自己 `CreateDIBSection` + `LockBits` + `RtlMoveMemory`。
2. **文字必须用 GDI+ `DrawString`**，不能用 `TextRenderer`（GDI）—— 后者不写 alpha，
   文字周围会留不透明底色块。
3. **`OnPaint` 里不能往窗口 DC 上画** —— 分层窗口内容完全由 `UpdateLayeredWindow` 决定，
   子控件画的任何东西都会被丢弃。所以 `BoxView.OnPaint` 只负责触发渲染，真正绘制在
   `PaintInto(Graphics)`。

**两条重要推论**（都踩过）：
- 圆角**不能靠窗口 `Region`**：分层窗口自带按 alpha 的命中测试，再套 Region 等于裁两遍，
  部分系统上会让内容整块不显示。改成在位图里 `SetClip` + 圆角路径（四角 alpha=0）。
- **子控件永远画不出来** → 就地改名必须用独立顶层小窗 `UI/RenameBox.cs`。

#### 3.4.3 图标提取高清管线

```
① 按需取档、命中即停
   目标 ≤48px 时以 ExtraLarge(48) 打头 —— 既「不小于目标」又「最小的那档」，一次命中，不碰 256 档
   达标判据：HICON 真实像素 ≥ 目标  且  内容占比 ≥ 30%  且  非畸形资源
② 原样渲染
   DrawIconEx 的 cx/cy 传 HICON 内部位图的真实尺寸（1:1），不缩放 → 拿到无污染的原始像素
③ 纯字节级面积平均（area/box filter）
   在预乘 alpha 空间做加权平均再还原 —— 缩小场景下这才是真低通，不像双三次会振铃
④ 畸形资源修正
   有效内容贴住左上角「且」面积占比 ≤50%（如 Cheat Engine 3%）→ 按包围盒裁出后重新铺满
⑤ 1:1 直贴
   缓存位图尺寸等于目标尺寸时用 DrawImageUnscaled，零重采样
```

**多级回退**（保证永不出现黑方块）：

```

   ↓ 黑图 / 失败

   ↓ 黑图 / 失败
按扩展名取通用图标
   ↓ 黑图 / 失败
手绘中性占位图
```

```

  ① 静默 ≥ 4 s

```

## 4. 关键设计决策与踩坑沉淀

这一节是本项目最有价值的资产：**每一个坑都有一条「怎么发现」+「怎么修」+「怎么防止复发」的完整闭环**。

| # | 坑 | 现象 | 正解 | 怎么发现的 |
|---|---|---|---|---|
| 1 | `Icon.ToBitmap()` 丢 alpha | 透明区域变**纯黑方块** | 用 `DrawIconEx` 画到 32bpp ARGB | 截图对比 |
| 2 | `SHGetFileInfo(SHGFI_ICON)` 对 .lnk 返回空 | 一批快捷方式**全黑** | 改走 `SHGFI_SYSICONINDEX` + `SHGetImageList` | 逐项打印图标溯源 |
| 3 | 用假路径探测图标 | 拿不到程序专属图标 | 路径存在时用真实路径，否则才 `SHGFI_USEFILEATTRIBUTES` | 视觉核对 |
| 4 | `DrawIconEx` 直接缩放 | 256→40 走 GDI 老缩放，边缘锯齿 | 原样渲染 + GDI+ 高质量缩放两段式 | 放大截图比对 |
| 5 | 无脑优先 Jumbo(256) | Cheat Engine 等在 256 档是「大画布+角落小图」，缩完只剩一点 | 按内容占比评分，取最合适一档 | `--iconprobe` 直方图 |
| 6 | 畸形判据写成「只看贴边」 | 八成正常图标被判畸形，每图标渲染 **2.6 次**，私有内存 +11.2 MB | 判据必须是「贴左上角 **且** 占比 ≤50%」 | `--memstep` 的图标管线统计 |
| 7 | 跨进程读到的「索引」不是同一张表 | ListView 索引查 Imagelist → 此电脑变硬盘、回收站变带叉驱动器 | 走 `SHParseDisplayName` + `SHGetFileInfo(SHGFI_PIDL)` 官方路径 | **拿 8 个两项都能取到的样本做交叉验证** |
| 8 | `ArrangeIfOverlapping()` 调用时机太早 | 格子还是 0 项时量出塌陷尺寸 → 误判重叠 → 写盘 → **永久抹掉用户布局** | 挪到 `RefreshAll()` 末尾，且只在首次灌入内容时执行 | 用户报「位置又没记住」 |
| 9 | 自绘拖动用 `_drag` 标志 + 窗体 `MouseUp` 复位 | 鼠标在窗口外松手时收不到 MouseUp → 此后鼠标经过标题栏窗口就跟着飘 | 交给系统拖动（`ReleaseCapture` + `WM_NCLBUTTONDOWN/HTCAPTION`），不留状态 | 用户报「鼠标移上去整个界面跟着动」 |
| 10 | 分层窗口里塞 `TextBox` | 窗口存在、`Focused=True`，但**屏幕上永远看不见** | 用独立顶层小窗承载输入框 | 枚举子窗口发现 `WindowsForms10.Edit...` 就在那儿 |
| 11 | WinForms 最小跟踪宽度 | 78px 的编辑框被撑到 **136px**，压到邻居图标上 | `AutoScaleMode.None` **且** `MinimumSize=(1,1)` | 打印编辑窗实际矩形 |
| 12 | `InvokeCommand` 返回 `E_INVALIDARG` | 「属性」对话框弹不出来 | 命令 id 必须**减 `idCmdFirst`** | 改 `[PreserveSig]` 拿到真实 HRESULT |
| 13 | `SetParent` 坐标系数 | 格子整体被挪出屏幕 | 父窗口客户区原点 ≠ (0,0)（本机 `(0,-678)`）；每次提交后用 `GetWindowRect` 复核落点自动修正 | `DESKLITE_TRACE_ULW=1` |
| 14 | 设置窗写死高度 + `AutoScroll` | 滚动条 + 最后一段说明被裁 | 每页上报内容底部，窗体高度自适应 | 截图核对三页 |
| 15 | 合成鼠标点击不会转移前台焦点 | 测试里按键被别的前台窗口吃掉 | 验证输入用 `PostMessage(WM_KEYDOWN/WM_CHAR)` 直接投给 Edit 子控件 | 测试脚本反复失败 |
| 16 | **测量本身污染被测对象** | 「212 句柄」的假数据 | 桌面图标是**全局状态**：残留实例会让新实例退化成「第二实例」，并把图标一直藏着 | 对比两次测量差异过大 → 查进程列表 |

> **方法论沉淀**：第 6 条和第 16 条是同类教训——**光看总量永远找不到 bug**。
> 第 6 条里真正 new 出来的位图合计只有 1.0 MB，而常驻涨了 14.5 MB，真因是「多做了 2.6 倍」；
> 第 16 条里两次测量差一倍，真因是「环境里有残留实例」。
> **先做归因（谁在分配 / 谁在改状态），再谈优化。**

## 5. 资源占用实测（2026-10-16 复核）

### 5.1 测量协议（重要）

桌面图标是**全局状态**，任何残留实例都会让新实例退化成「第二实例」并把原生图标一直藏着，
从而测出假数据。因此测量必须遵守：

```
① 开场断言：无 DeskLite 实例 + 桌面 ListView 可见（否则中止）
② 拉起 → 预热 16 s → 采样 30 s
③ 收场：--quit 干净退出，并断言 ListView 重新可见
```

> 脚本：`outputs/steady.py`（稳态）、`outputs/curve2.py`（启动曲线）、
> `outputs/stress.py`（长跑稳定性）。

### 5.2 稳态对比（同一环境、同一协议）

| 版本 | 工作集 | 私有内存 | 句柄 | GDI | USER | CPU |
|---|---:|---:|---:|---:|---:|---:|
| 改动前 `1711ea0` | 12.5 MB | 28.7 MB | 619 | — | — | 0.000 % |
| `f4b616d`（P0 之前） | 13.2 MB | 29.0 MB | 618 | 89 | 50 | 0.007 % |
| `f4b616d` 同环境复测 | 12.2 MB（区间 8.9~21.9） | 22.6 MB | 482 | — | — | 0.008 % |
| **P0 修复后** | **11.0 MB（区间 10.1~11.4）** | **22.0 MB** | **481** | **88** | **44** | **0.000 %** |

**结论：P0 三项修复没有带来任何常驻开销增长。**
私有内存 22.0 vs 22.6 MB、句柄 481 vs 482、CPU 0.000 % vs 0.008 % —— 差异全在噪声内，
工作集反而更低且**波动区间明显收窄**（10.1~11.4 vs 8.9~21.9），这是整理介入更及时的结果。

> 早期记录的「9.0 MB / 22.2 MB / 498 句柄」来自另一会话、另一桌面状态，与上表不可比。

### 5.3 冷启动曲线

```
时刻      工作集    私有     说明
0.07 s     9.4 MB    1.7 MB  运行时初始化
0.15 s    23.3 MB    6.7 MB  WinForms 初始化

1.06~2.9   88.0 MB   28.0 MB  维持
2.91 s     3.7 MB   28.9 MB  ★ 一次性内存整理（释放图标池 + 双轮 GC + Trim）
3.2 s      5.3 MB   28.9 MB
~20 s     12~13 MB   29.0 MB  被定时器逐页换回，落在稳态
```

**尖峰 88 MB 的归因**（用 `DESKLITE_ICONSTUB=1` 做对照）：

| 配置 | 峰值工作集 | 私有内存 |
|---|---:|---:|
| 完全不碰 shell 与 GDI+（只手绘占位图） | 76.9 MB | 25.5 MB |
| 当前完整流程 | 88.0 MB | 29.0 MB |
| **差值（图标管线成本）** | **11.1 MB** | **3.5 MB** |

也就是说：**88 MB 里有 76.9 MB 是 .NET 运行时 + WinForms 的底噪**（JIT 与框架程序集页），

### 5.4 长跑稳定性（8 轮「桌面变更 → 刷新」）

`stress.py` 现在会在压测后**再静默观察 30 秒**，把「活动期临时水位」和「真泄漏」分开 ——
常驻托盘程序真正要排除的是后者。

| 指标 | 基线 | 8 轮后（活动中） | 静默 +30 s | 判定 |
|---|---:|---:|---:|---|
| 工作集 | 10.3 MB | 40.9 MB | **8.0 MB** | 活动期水位，5 s 内即掉回 |
| 私有内存 | 22.1 MB | 23.8 MB | **22.1 MB** | ✅ 完全回落 |
| 句柄 | 479 | 505 | **498** | 回落，残留 +19 |
| GDI | 86 | 88 | 88 | +2 |
| USER | 44 | 46 | **44** | ✅ 完全回落 |

**结论**：
- ✅ **没有泄漏**：私有内存、USER 静默后完全回到基线，句柄也在回落通道上。
- 活动态真实占用约 **41 MB 工作集 / 24 MB 私有**（此前 README 的「9 MB」是整理后的人为低水位）。
- 句柄 +19 是**两版共有的固有值**（图标缓存 / 监听器的持久句柄），不是本轮引入：
  同脚本测 `f4b616d` 得到的是**完全相同的 +19 / +2 / ±0**。

### 5.5 空闲回落速度（P0-② 验收）

`settle_probe.py`：触发一次桌面刷新把工作集推上去，测它回到 < 16 MB 需要多久。
第 2 轮起都在「上一轮刚整理完」之后立刻触发，**天然构成最坏情况**（冷却几乎从头吃满）。

| 版本 | 最坏回落 | 平均 |
|---|---:|---:|
| `f4b616d` | **28 s** | 27.5 s |
| P0 修复后 | **6 s** | 6.0 s |

修法：冷却按水位分档（高于水位线用 6 s、贴近水位线用 30 s）+ 巡检间隔自适应
（刚活动过 2 s、稳定后 5 s）+ 「整理无效」时指数退避（8s→16s→32s→60s 封顶）。

> 中途踩过一个坑：水位线原本取 26 MB，而一次刷新的水位是 24~26 MB ——
> **两者重叠**，于是每次巡检都走「已经够小、不用管」分支，而那个分支又顺手刷新了冷却计时，
> 结果整理被无限期推后（实测出现过 22 s 不回落）。修正为：水位线降到 16 MB（与活动态拉开距离），
> 且「不用管」分支**不再触碰冷却计时**。修正后 4 轮实测稳定在 6.0 s。

### 6.1 ✅ 圆角 Region 的释放时机（原「GDI Region 泄漏」——已修，且性质经实测厘清）

**位置**：新增 `Shapes.ApplyRoundedRegion`；调用点 `UI/BoxForm.cs`、`UI/SearchForm.cs`、`UI/SettingsForm.cs`

原写法（三处 `OnResize` 各一份）：

```csharp
protected override void OnResize(EventArgs e)
{
    using var path = Shapes.RoundedPath(new Rectangle(0, 0, Width, Height), CornerRadius);
    Region = new Region(path);     // ← 旧 Region 失去引用，只能等 GC 走终结器
}
```

`Control.Region` 的 setter 不接管所有权；而 `OnResize` 在拖动改尺寸时会连续触发几十次。

**但「GDI Region 泄漏」这个说法是不准的。** 2026-10-16 加 `--gdiresize` 做**分进程对照**后厘清：

| 测量（各 20000 次改尺寸） | GDI 句柄 Δ | 私有内存 Δ（GC 后） |
|---|---:|---:|
| 裸窗口（`OnResize` 什么都不做） | **0** | +4856 KB |
| 带圆角 Region（旧写法） | **0** | +6192 KB |
| 带圆角 Region（新写法） | **0** | +6072 KB |

- `System.Drawing.Region` 底层是 **GDI+ 的 `GpRegion`，不计入 GDI 句柄表** ——
  `GetGuiResources(GR_GDIOBJECTS)` 全程恒定（41 → 41），**不存在 GDI 句柄泄漏**。
- 那 6 MB 里有 **4.9 MB 来自「改窗口尺寸」这件事本身**（裸窗口同样涨），
  扣掉之后 Region 的净成本约 **1.4 MB / 20000 次**，新旧写法**无差异**（都在噪声内）。
- 真实性质是**释放不及时**：Region 有终结器兜底，最终会被回收，只是要排队。

**改法**：`Shapes.ApplyRoundedRegion(Control, radius, ref holder)` —— 先赋新、再 `holder?.Dispose()`、
最后换 holder；`radius = 0` 表示不要圆角（分层窗口自带 alpha 裁剪），同样释放旧的。
好处是把「等 GC 决定何时还」换成「换下去就立刻还」，少一批对象排在终结器队列里，
所有权也一眼看得出。**代价：无**（实测私有内存与 GDI 均无变化）。

**验收**：`DeskLite.exe --gdiresize 2000 region` → GDI 恒定、判定 PASS。

> 教训：**先做对照，再下结论**。第一版探针只测「带 Region 的窗口」，看到 +6 MB 就写成了
> 「每次 OnResize 泄漏一个 GDI 对象」——实际上 GDI 一个都没漏，那 6 MB 主要是改尺寸本身的
> 系统开销。加了裸窗口对照组才把账算清。

### 6.2 ✅ 空闲内存整理回落滞后（已修）

**原现象**：活动后工作集停在 ~43 MB，需要「静默 4 s + 轮询最多 5 s + 冷却 30 s」≈
最多 **39 秒**才会被压回 13 MB。
**成因**：`SettleCooldownMs = 30_000` 是固定值，不区分「刚经历一轮活动」和「一直空闲」。

**修法（三层）**：
1. **冷却按水位分档** —— 高于水位线用 `6 s`，贴近水位线用 `30 s`；
2. **巡检间隔自适应** —— 刚活动过 2 s、稳定后自动放稀回 5 s（否则常驻 CPU 会从 0.00x% 抬到 0.04%）；
3. **无效退避** —— 某次 trim 后水位几乎没降（说明页面真在用），指数拉长间隔 8s→16s→32s→60s 封顶，
   避免与系统页调度互相拉扯。

**结果**：最坏回落 **28 s → 6 s**（见 5.5），稳态 CPU 仍为 **0.000 %**。

### 6.3 ✅ 强杀后桌面图标保持隐藏（已加固；强杀本身是物理限制）

**问题**：进程被强杀时桌面原生图标会一直保持隐藏，直到下次启动 DeskLite 才还原。

**已做的三层加固**：

| 层 | 内容 |
|---|---|
| ① 进程退出路径补全 | `AppDomain.ProcessExit`（覆盖 `Environment.Exit`、控制台关闭、Ctrl-C）+ `WM_ENDSESSION`（注销 / 关机）。后者由一个**纯 Win32 隐藏消息窗**（`MainContext.SessionWatcher`）接收 —— 格子被 `SetParent` 到 Progman 后是子窗口，收不到只发给顶层窗口的广播；而**刻意不用** `SystemEvents.SessionEnding`（那会常驻一个系统事件线程 + 隐藏窗口）。 |
| ② 落盘标记自愈 | `desktop_hidden.lock` + 启动时 `RecoverIfNeeded()` 无条件还原，并弹托盘气泡告知。 |
| ③ 触手可及的救援入口 | 桌面右键菜单新增「还原桌面图标」→ `--restore`。注册表项是持久的，**进程死了照样能用**。命令会检测主实例是否在运行并如实提示（否则图标几秒后又会被接管隐藏，用户会以为没生效）。 |

**强杀（`TerminateProcess`）本身无解**：内核不给被杀进程任何执行机会，挂多少个处理器都一样。
覆盖它只有两条路 —— 引入第二个常驻看门狗进程、或把图标改成「遮挡」而非「隐藏」；
前者与本程序「只跑一个进程」的定位冲突，后者要求格子铺满整屏才成立。
所以选择**把恢复入口做到触手可及**：

| 恢复方式 | 代价 |
|---|---|
| 桌面右键 → 桌面整理 · 精简版 → 还原桌面图标 | 1 次点击 |
| 重新启动一次 DeskLite | 自动自愈（落盘标记） |
| 重启 explorer / 重启系统 | 系统行为，自动恢复 |

**验收**（`outputs/kill_recovery.py`，全项通过）：接管生效 → `taskkill /F` 后确实停在隐藏态 →
`--restore` 恢复且清标记 → 再次启动时日志出现「检测到上次未正常退出…已自动还原」。

### B.3 方法学教训（值得记住）

1. **测量本身会污染被测对象** —— 残留实例会把桌面一直藏着并让新实例退化成「第二实例」，
   测出过「212 句柄」这种假数据。为此定了三步协议（测前断言、测后还原）。
2. **先做对照，再下结论** —— §6.1 那条「GDI 泄漏」就是只测了一组、没做基线的产物。
3. **阈值要和应用场景拉开距离** —— 水位线 26 MB 与活动水位 24~26 MB 重叠，
   直接导致整理被无限推后（见 5.5 的坑）。
